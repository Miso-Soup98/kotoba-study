# Windows guard regression tests

Copy these three `.mjs` files into `APP/tests/windows/`. They exercise the real
`../../scripts/run-bounded.mjs` and real Windows Job Objects. They do not start
Vite, Wrangler, browsers, or a memory stress workload.

Optional Windows-only command, separate from the default cross-platform tests:

```sh
node --test tests/windows/bounded-run.test.mjs
```

An optional package script can be named `test:windows-guard`. On other operating
systems the six tests are skipped. Node 22.13+ and 64-bit PowerShell are required.

Coverage: normal exit, timeout, forcibly closed wrapper, forcibly closed guard,
preflight refusal, output-log ceiling. Each launched fixture checks arguments
containing spaces, Chinese/Japanese, quotes, a trailing backslash, and an empty
string. The preflight case intentionally starts no fixture.

All files generated by the tests live in a new `os.tmpdir()` directory per case;
its location is reported as a diagnostic. No APP files are written. Small logs
remain there for inspection, especially when a test fails.

Fixture parent and child each have an independent shared expiry of at most
25 seconds; the driver has a separate 28-second deadline. The driver observes
the exact native `ChildProcess` returned by the real spawn call, so the forced
guard-close test uses its owned handle instead of searching process names or
terminating a PID. Test cleanup always runs in `finally`, asks the driver to
close its guard, and then terminates only the wrapper it created. Process PID
checks are read-only; no unrelated Node, PowerShell, or browser is stopped.

The output-ceiling fixture generates about 1.25 MiB/second with backpressure;
its test ceiling is only 1 MiB. The process Job cap is 256 MiB, with an assertion
that observed private memory stays below 128 MiB. It never allocates up to the
Job limit. This checks containment/cleanup and argument passing, not leak absence
or the cause of the reported machine freezes.

This revised portable-path candidate has been syntax-checked only. The earlier
six equivalent scenarios passed before this cleanup; rerun from the actual APP
paths after integration.
